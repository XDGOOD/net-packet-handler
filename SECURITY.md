# Security Policy & Architecture - AEGS v6.0 Titan

## 1. Threat Model & Overview

**AEGS (Aegis Encrypted Gateway Suite) v6.0 Titan** is designed to operate over hostile, untrusted, and censored networks. The security architecture addresses:
- **Active Traffic Analysis & Deep Packet Inspection (DPI)**: Obfuscation of handshake and transport packets via dynamic RFC 9000/9369 QUIC Initial mimicry and STUN decoys.
- **Active Probers & Scanning Infrastructure**: Blackhole responder strategies mimicking real QUIC/HTTP3 servers while strictly limiting response sizes to mitigate amplification attacks.
- **Replay Attacks**: Two-phase anti-replay filtering separating uncommitted inspection from authenticated state mutation.
- **Traffic Leaks**: Strict fail-closed KillSwitch and DNS Leak Protection guaranteeing no plaintext network egress.
- **Denial of Service (DoS)**: Bounded memory buffers, microsecond AIMD backpressure pacing, and O(1) eviction for handshake queues.

## 2. Core Security Mitigations

### 2.1 Fail-Closed KillSwitch & DNS Leak Shield
- **Transactional State Machine**: Firewall configuration is managed through four distinct phases: `Prepare` -> `Apply` -> `Verify` -> `Commit` (or `Rollback` on failure).
- **Enforced Return Code Validation**: In `client.cpp`, `kill_switch.enable(...)` and `dns_shield.enable(...)` are checked immediately. If rule application or routing fails (due to insufficient privileges or environment errors), the client process terminates with `EXIT_FAILURE` (`return 1;`). It never falls back to an unshielded network state.
- **Atomic Teardown**: Graceful signals (`SIGINT`, `SIGTERM`) and failure paths trigger automatic restoration of `/etc/resolv.conf` and teardown of firewall chains.

### 2.2 Two-Phase Anti-Replay Verification
- **Vulnerability Addressed**: In conventional single-phase filters, updating sequence window state before authenticating the MAC or AEAD tag allows an unauthenticated attacker to inject spoofed sequence numbers that permanently advance the window and drop legitimate traffic.
- **Two-Phase Commit Design**:
  1. `check_peek(uint64_t seq)`: Read-only query checking whether the sequence number is duplicate or outside the sliding window. Performed *before* crypto decryption.
  2. `update_commit(uint64_t seq)`: Commits the sequence number into the sliding bitmask *only after* ChaCha20-Poly1305 AEAD tag authentication succeeds.
- Integrated across `network_security.h`, `session.h`, `server.cpp`, and `client.cpp`.

### 2.3 Buffer Safety & Jumbo MTU Support
- **Dynamic MTU Clamping**: MTU is clamped within safe RFC standards (`576 <= MTU <= 9000`) in `aegs_config.h`.
- **9216-Byte TX Slot Buffer**: `TxSlot::data` and `PacketScratch` buffers are sized to `9216` bytes (`TX_SLOT_SIZE = 9216`), fully accommodating Jumbo Ethernet frames (up to 9000 MTU) plus encapsulation, padding, and QUIC mimicry headers without memory overflow or truncation.
- **Oversized Packet Accounting**: Out-of-bounds frames increment `dropped_oversized` metrics rather than causing silent corruption or undefined behavior.

### 2.4 Anti-Amplification Defenses (RFC 9000 Compliance)
- **Amplification Factor < 3x**: Per RFC 9000 §8.1, servers responding to unvalidated UDP addresses must not exceed 3 times the received datagram size.
- **Clamped DCID & Response Size**: In `blackhole_responder.cpp::quic_retry`, prober Destination Connection IDs (DCID) are clamped to a maximum of 8 bytes (`probe_dcid_len <= 8`).
- Total response datagram length is strictly capped at **55 bytes**, which remains well under 3x for any valid minimum probe (>= 20 bytes).

### 2.5 Safe Subprocess Execution (`safe_exec`)
- All system utility invocations (e.g. `iptables`, `ip6tables`, `ip`, `netsh`, `resolvectl`) utilize tokenized argument vectors (`std::vector<std::string>`) executed directly through `fork()` and `execvp()`.
- Shell interpreters (`/bin/sh -c`) and string concatenation are prohibited in rule application paths, eliminating shell command injection vulnerabilities.

### 2.6 File Permissions & Key Protection
- **Server Database & Working Directories**: In `scripts/init_db.sh` and server startup routines, storage directories are hardened to `0700` (`drwx------`) and SQLite database files to `0600` (`-rw-------`).
- **Static & Ephemeral Keys**: Private keys loaded or generated by `handshake.cpp` (`load_or_generate_key`) are verified for exact byte length (32 bytes), validated against OpenSSL `EVP_PKEY`, and enforced with file mode `0600`.

### 2.7 O(1) Queue Eviction & Handshake Resource Bounding
- Handshake deduplication and pending authentication tables use dual-indexing: an `std::unordered_map` for O(1) cryptographic lookups and a time-ordered `std::deque` for O(1) chronological eviction.
- Replaces linear O(N) table sweeps over high-volume tables (up to 100,000 entries), preventing algorithmic complexity Denial-of-Service attacks.

### 2.8 Cryptography & Perfect Forward Secrecy
- **X25519 Elliptic Curve Diffie-Hellman (ECDH)** for ephemeral key exchanges during initial handshakes and PFS session resumptions.
- **ChaCha20-Poly1305 AEAD** (RFC 8439) with 96-bit nonces composed of 64-bit monotonically increasing sequence numbers and 32-bit random session prefixes.
- **HKDF-SHA256** (RFC 5869) for directional key derivation (`c2s` and `s2c`).

## 3. Vulnerability Reporting

If you identify a security vulnerability or weakness in the AEGS protocol or its reference implementations, please disclose it responsibly:
- **Email**: security@aegs-project.org
- Please do not file public issues on GitHub for undisclosed security vulnerabilities.
